# Summary publication recovery

Source support for an explicit publication judge migration over an existing final
summary capture. This document does not establish installation, runtime recovery,
provider success, measured cost, or validation results.

## Scope and prerequisites

The internal SDK functions are registered with `registerSummaryQueueFunctions`;
there is no new REST endpoint or MCP tool. They support one retained final unit,
an existing complete evidence root, and unchanged original sources. The job must
be pending or failed specifically with `summary_publication_pending`. Recovery
jobs, hierarchical evidence, missing captures, changed generation input, and a
conflicting active job are rejected. No summary generation or queue enqueue occurs.

The existing v3 publication checkpoint must be intended, without response or
overflow, with `executor_error` or HTTP 400 diagnostic. The shared migration
implementation binds its exact identity and record fingerprint to a v4 request
and the full current `publication-verdict-v2` / `closed-json-verdict-v2` contract.
Older evidence remains authoritative; captured or decided checkpoints cannot
be superseded. Reflection migration behavior is preserved.

## Read-only preparation

Call `mem::summary-publication-prepare` through the existing iii SDK:

```typescript
const prepared = await sdk.trigger({
  function_id: "mem::summary-publication-prepare",
  payload: {
    jobId: "sqj_mvcv2ttj_fe88cd437c6f",
    unitId: "squ_mvcv2ttj_4b3b2d9ac8b1",
    dispositionId,
    budget: { windowId, ceiling: 1 },
  },
});
```

`dispositionId` and `windowId` are explicit operation identifiers matching
`validBudgetId`; neither is a credential or authorization token. Choose a new
disposition identifier with the existing `generateId()` convention and the native
controller's approved budget window identifier.
Preparation reads StateModule, verifies retained capture/source bindings, and
uses a fresh executor's preparation method. It performs no writes, HTTP requests,
provider calls, native budget claims, or grant creation. Its response contains
`admission` with version, exact capture identity/fingerprint, the returned judge
disposition, and `attemptId`. Preserve this envelope unchanged.

## Native grant and admission

Main provisions the existing private operator configuration file
`<canonical DB directory>/provider-budget-grants.json`, preserving its required
ACLs. This is grant configuration, not an API token. Main's native source reading
identified the existing `Grant` v1 shape: `window: { id, startsAt, expiresAt,
ceiling }`, `allowedEndpoints`, and `operations: [{ id, ceiling, context? }]`.
Window timestamps use canonical UTC milliseconds and span at most seven days.
An extension is append-only with unchanged window, endpoints, and prior
operations. See [provider attempt budgets](provider-attempt-budget.md).

These TypeScript functions create no native grants and expose no grant-preparation
API. Main owns private file provisioning after preparation returns the exact
attempt and capture identifiers. Do not fabricate grant tokens or reconstruct
opaque native payloads. No direct SQL or new native API is needed.

The engine injects `_caller_worker_id` into SDK object payloads. These controls
validate and remove that transport field before checking the closed application
envelope. All other unknown application fields remain rejected; caller metadata
is excluded from the retained admission and capture identity.

Bind the native authorization to:

| Field | Value |
| --- | --- |
| operation ID | `prepared.admission.attemptId` |
| window and ceiling | `prepared.admission.disposition.budget` (ceiling exactly 1) |
| workflow | `summary` |
| function ID | `mem::summary-publication-admit` |
| source ID | `prepared.admission.capture.sessionId` |
| job and unit IDs | `prepared.admission.capture.jobId` and `.unitId` |
| phase | `publication` |
| continuation ID | `prepared.admission.capture.captureFingerprint` |

Then call `mem::summary-publication-admit` with **the returned admission object as
the entire payload**. It does not accept manually assembled candidate/source text.
The existing `withProviderAttemptBudget` transport requires fresh native claim
and consume acknowledgments before dispatch. Missing transport, denied grants,
exhaustion, or ambiguous acknowledgments fail closed.

The existing `createProviderAttemptBudgetTransport(sdk)` sends each validated request to
`sdk.trigger({ function_id: "state::storage", payload: request })`. Its supported
actions are `provider_budget_claim`, `provider_budget_consume`,
`provider_budget_finish`, and `provider_budget_status`; there is no preparation or
grant action in this transport. The claim generated by `withProviderAttemptBudget`
contains `action`, `operation_id`, `window_id`, `expected_ceiling: 1`, a freshly
generated `claim_id`, and `context` containing the exact fields in the table.
The transport validates capability `state::provider_attempt_budget_v1` and fresh
acknowledgments. Native `state::storage` claim fixes the configuration and
registration before consume commits. Operator provisioning must precede
admission, since a denied
or unknown attempt is retained rather than reset for another dispatch.

Admission persists its capture journal and the shared migration's new intention,
supersession link, and budget binding before provider dispatch. It prepares a
fresh executor and compares the full target contract. Logical JSON schema remains
in the captured contract; a `validated-json-text` provider profile selects its
supported transport without an unsupported `response_format` HTTP parameter.

Only a supported judge verdict permits canonical summary publication through
the existing completion path, with foreground completion suppressing automatic
follow-up queue work. The failed job is never reset to pending. Existing effect
receipts support interrupted completion; completed replay checks the effect and
canonical summary against the journal. Unknown attempts remain consumed. Exact
replay follows the existing selected checkpoint without provider redispatch;
different admission, capture, source, contract, or budget is rejected.

## Local replay of an oversized captured diagnostic

The source implementation also supports `publication-reason-projection-v1` for
retained v4 captured or decided responses. The provider's original
`publication-verdict-v2` contract and `closed-json-verdict-v2` parser still require
at most 512 Unicode code points. An oversized original does **not** satisfy that
contract. The strict parser continues to reject it; the explicit diagnostic
projection runs only after the raw response has been durably captured.

During checkpoint resolution, a closed response whose sole defect is a
reason longer than 512 code points can yield a derived diagnostic. The original
reason remains bounded by 2,048 UTF-8 bytes and 2,048 code points; the whole raw
response remains bounded by 16,384 bytes. The same exact two-key JSON grammar,
duplicate-key and escaped-alias rejection, closed verdict enum, optional exact
outer JSON fence, nonempty reason, and control-character restrictions apply.
Unknown intended dispatches, overflow records, extra fields, prose, and ambiguous
responses are not recovered by this projection.

Resolution runs immediately after the first durable capture as well as on local
replay. A provider execution followed by local projection returns `replayed:
false`; resolving an already retained response returns `replayed: true`. Local
normalization does not imply that the initial provider request was free or absent.
The separate derivative stores diagnostic evidence without an invocation replay
flag. Earlier derivative records containing a replay flag remain compatible;
each invocation's returned flag is determined by its execution path.

The verdict is preserved exactly. The diagnostic is a prefix followed by
` [diagnostic excerpt; full reason retained]`, totaling 512 code points. The
result's `normalization` contains the version, explicit original-contract failure,
original full reason, original and projected lengths, source-record fingerprint,
and raw fingerprint. An idempotent `publication-reason-projection_*` record in the
existing state scope retains this derived result. Original raw, request identity,
decision, contract, supersession links, and budget binding are not rewritten.
Historical checkpoint observations retain their original meaning and identity.

For consolidation admission journals retaining `invalid_response` with reason
`closed_verdict_required`, `mem::consolidation-publication-admit` reconciles the
same admission through existing checkpoint selection. That replay branch forbids
provider dispatch even if state unexpectedly leads toward execution. On success
the journal retains the prior result in `priorResults` and stores the derived
result. No new admission, grant, budget reset, provider attempt, or endpoint is
needed. A captured `unsupported` verdict continues as `unsupported`; projection
does not authorize publication of an unsupported candidate.
