# Git snapshots

This document accompanies a prepared source candidate. Native compilation, isolated native fixtures and installed acceptance have not run. Do not infer installed snapshot correctness from the mocked TypeScript proofs.

`mem::snapshot-create` writes `state.json` in the configured snapshot directory and commits it to its local Git repository. `SNAPSHOT_ENABLED=true` enables the periodic timer; `SNAPSHOT_INTERVAL` sets its interval in seconds (default 3600). The default directory is `~/.agentmemory/snapshots`.

Snapshot creation streams sessions, memories, graph nodes, per-session observations and access logs from one completed engine-owned private database copy. Every collection uses bounded key pages followed by sequential complete-row reads through `state::storage`. The copy is addressed by an opaque handle, a process generation and exact owner/request identifiers. There is no fallback to live pagination on engines without the new snapshot actions. No MCP tool or REST endpoint is added.

The engine's existing SQLite worker owns both the live source connection and the stepped SQLite Backup lifetime. It copies at most 1 MiB per step and runs up to eight foreground jobs between steps using the same `&Connection`. Foreground write transactions remain Immediate via `Transaction::new_unchecked`. The cut is the database state when Backup returns Done. Backup and the destination connection are dropped before a private read-only connection opens. Graph recovery, active graph leases and incomplete callback receipts are checked in the completed copy. A refused cut is deleted; writers continue and their changes are not rolled back. Creation does not acquire the batch mutation lock. Restore retains that lock and its existing graph job/provenance behavior.

This mechanism deliberately does not keep a long read transaction on the live WAL. The existing WAL policy still attempts PASSIVE checkpoints at 32 MiB and refuses growth at 64 MiB if checkpointing is blocked. The intended same-owner backup updates and checkpoint compatibility require actual native proof before integration acceptance; a separate pinned WAL reader is insufficient.

Complete original records, metadata, nested provenance, JSON fields and counters are preserved. A second session-key scan supplies observation scopes without retaining the complete session catalog. Serialized records use compact JSON within the existing snapshot document schema. Memory includes a complete row, decoded JSON trees and serialization strings. No corpus is hydrated in memory. The copy and reader each use an 8 MiB SQLite cache, never simultaneously; the original 64 MiB source cache remains unchanged. Stored+logical decode work is limited to 32 MiB per row; JSON object overhead is additional and must be measured in native/runtime acceptance. These byte limits are not a hard whole-process RAM guarantee.

## Limits and lifecycle

The adapter keeps its existing 64 MiB admission ceiling, approximately 16 MiB structural envelope, 32 queue slots, 32 queue waiters and 60 s ordinary queue wait. One capture slot admits at most one queued/running capture. Capture optionally occupies one ordinary queue slot and refuses a full queue without adding a waiter. Capture and each read reserve an existing envelope-sized admission permit; no admission limit is raised.

Capture has a 300 s request deadline, at most 1,000,000 backup steps and at most 1 MiB copied per step. Export has an absolute 600 s lifetime from completion, no refresh. Read/cancel requests have a 10 s queue/response deadline; private SQL reads have a 3 s progress-handler limit. Each key page has at most 256 keys/1 MiB, each key/scope at most 4096 bytes, each view at most 100,000 pages, 10,000,000 enumerated keys and 16 outstanding single-use scope-bound cursors. Full row logical JSON is capped at 16 MiB minus 128 KiB, preserving a complete 15 MiB original within the existing transport envelope.

Existing ordinary jobs have no general operation deadline. Capture checks cancellation/expiry between foreground jobs and backup steps; it does not preempt a foreground job already running or an operating-system filesystem call. The caller deadline is finite, but cleanup latency has no absolute engine-wide wall-clock bound in that situation. Native fairness/cancellation tests and installed observations must assess this limitation explicitly.

At most one native view exists. Native copy plus its journal/WAL/SHM sidecars has a 12 GiB ceiling; a destination page cap, live source-page checks, step/footprint checks and free-space checks enforce it. The copy stops before crossing the ceiling, including source growth between steps. Native preflight reserves the complete 12 GiB native plus 4 GiB publication ceiling and 64 MiB free-space margin. The application independently reserves 4 GiB on the snapshot filesystem. That publication budget accounts for the existing `state.json`, the new temporary JSON, a second new-JSON-sized Git publication allowance and 16 MiB headroom. JSON output is refused once `oldBytes + 2 * newBytes + headroom > 4 GiB`. Existing permanent Git history is not a temporary copy and is not pruned by this change. Git object/index growth and destination page-cap behavior during same-owner automatic updates remain mandatory native/runtime gates.

Native close drops the reader before deleting its exact private directory. Cleanup failure retains the slot and retries through periodic reaping; there is no hidden archive. Cancellation during capture marks it cancelled while retaining its slot until Backup has dropped. A dropped caller future cancels its budget; lost worker acknowledgment triggers cleanup. A network-level lost acknowledgment still leaves an engine-owned expiring reservation. Idle worker reaping runs every 100 ms between ordinary jobs, with one diagnostic per continuous cleanup failure. The directory's `.owner.lock` stays exclusively locked for the adapter lifetime. On restart, the engine obtains that OS lock before removing the single validated `.view-<UUID>` leftover in `<database>.snapshot-readviews`, refuses unexpected/symlink entries or more than one leftover, and changes the generation. Another owner cannot delete an active owner's files. Old handles fail closed.

The writer uses a single exclusive `.state-snapshot.tmp` file and renames it over `state.json` only after every iterator and stream succeeds and native cleanup is acknowledged. Missing/mismatched rows, oversized values, invalid/stale/foreign/expired handles, cancellation, capacity refusal and transport/stream failures leave the previous `state.json` and Git untouched. Iterators close and the owning stream is destroyed before temporary-file removal. Failure never replaces records with empty arrays. Git commits follow successful publication; a Git failure after rename retains the published file and must be reconciled before retry, as in the existing contract. Concurrent requests in the daemon return `Snapshot already in progress`.

A pre-existing `.state-*.tmp` artifact blocks publication before view creation. It is counted as outstanding recovery state, not renamed to an archive, overwritten or blindly deleted. This prevents crash retries from accumulating copies. An authorized operator must establish that no publisher owns it and remove/reconcile that exact artifact before retry. The implementation scans at most 128 directory entries and otherwise fails closed. Installed restart recovery must demonstrate native cleanup and this explicit JSON-publication recovery path. The supported daemon has one snapshot publisher; concurrent separate daemon instances sharing a Git repository require an external publication ownership contract and are not newly supported.

## Integration and recovery gates

Failure cleanup attempts stream closure and owned temporary-file unlink independently. A rejected close wait cannot skip unlink. Cleanup diagnostics identify `stream_close` or `unlink`; the snapshot operation retains its primary failure. A focused real-Node WriteStream fixture injects an EIO close callback after actually closing the test descriptor, observes `error` then `close`, and proves unlink still succeeds without publishing or touching another owner's file. This is injected close-error behavior, not an observed physical disk EIO.

Apply the exact source delta only after the frozen native source owner permits integration and the recorded baseline matches. Cargo adds rusqlite's `backup` feature and `fs2 = "0.4"`; lockfile resolution and dependency compatibility require the exclusive native integrator. Do not build or install this candidate during another compiler owner's freeze.

Run the exact native filters listed in the scratch handoff using an isolated `III_SQLITE_TEST_ROOT`. Prove same-owner updates/deletes/creates across pages, complete 15 MiB originals, active/recovery cut refusals, stale/foreign handles, no WAL pin at the existing 64 MiB pressure boundary, fairness, injected disk/step/reader/cleanup faults, growth at the copy ceiling, cancellation/expiry/lost ACK, restart cleanup and released queue/admission permits. Fixtures use tiny copies and explicit test-only fault/capacity injection; a passing injected fixture alone does not prove actual 12/16 GiB physical accounting. Measure actual temporary files/sidecars and publication/Git growth in the installed acceptance gate.

Then prove one installed correlated snapshot while enabled normal writes continue, compare complete originals/provenance/counters to its recorded cut, verify cleanup after success/failure/restart and observe representative RAM settling. Approximately 1.6 GiB attributable to compaction is allowed by the current user criterion; attribution must be established and is not supplied by source tests. No source proof establishes service startup, an automatic cycle, production RAM or an installed repair.

Rollback before integration is deletion of this scratch candidate only. After integration, restore the exact prior source/dependency lock through the integrator, rebuild under the approved exclusive gate and reconcile any active native view/publication artifact before installing or restarting. Never delete source data, change credentials or rewrite existing Git snapshots as part of this rollback.

`mem::snapshot-list` lists the latest 20 Git commits. Restore retains its existing full-file read and JSON parse behavior; do not use restore of a large production snapshot as a low-memory validation. A successful source test does not establish an installed automatic cycle or production RAM consumption.
