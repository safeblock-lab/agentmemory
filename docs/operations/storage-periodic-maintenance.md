# Periodic storage maintenance

The existing local 60-second maintenance caller honors startup quiet mode. The admitted physical path uses a cooperative 45-second work window and yields while foreground requests are active or were active in the previous five seconds. It uses the existing native state-storage operations; no new timer, provider, or queue is introduced.

The foreground window applies to mutations, user search/context retrieval, full listings, MCP requests and unknown request shapes. Exact bounded dashboard observations do not extend it: health/status/liveness/config with empty query parameters, accepted previews, the latest-memory counter and bounded recent-session/crystal pages. Lesson preview reads now have their own first-page bound of five projected rows and 64 KiB; their total remains unknown, and the full lesson listing remains foreground work. This prevents dashboard refreshes from continually renewing the idle delay without weakening native pressure checks or storage fences. Physical responses separately identify `cancellationReason:foreground_pressure` or `deadline`; `null` means neither cancellation was observed during that invocation. See [compaction completion](compaction-completion.md) for scope and evidence limits.

The retention path maintains observation-index and cleanup progress separately from the admitted physical path. Logical cleanup is not counted as physical compaction. Native layout and periodic compaction work resume their saved jobs, cursors and exact pending requests across ticks.

When due, the caller drives native compaction through `compact_status` and bounded `compact_apply` batches: activate an idle migration, resume copy at the engine cursor, cut after native copy completion, then collect until the native receipt reports terminal GC completion. New collection requests use the existing native ceiling of 4096; other periodic steps retain 128. Both use a 1 MiB and 2.5-second request budget. Native collection keeps its internal 128-item chunks and enforces time, byte and candidate/deletion bounds. Existing pending requests and exact receipts are preserved. The larger limit can reduce SDK and receipt round trips but proves no processing rate or physical reduction. The admitted physical path can drain up to 1024 periodic steps within its shared 45-second window; deadline, foreground pressure, reconciliation and phase transitions can cut it short. Layout work gets up to four existing subwindows of 16 batches and five seconds each, subject to a shared cooperative 20-second deadline that reserves 25 seconds for periodic work and reclaim. Foreground pressure is checked between batches and before layout dispatch. An in-flight request may finish after the deadline; subsequent dispatch yields. Deploy this caller with the native control-record invalidation correction described in [compaction completion](compaction-completion.md); increasing the limit alone cannot fix repeated GC cursor resets caused by progress persistence.

Only the admitted automatic physical cycle uses reclaim maintenance mode (`maintenance:true`, `checkpoint:"truncate"`) with a 4,096-page and 3-second request bound; ordinary reclaim keeps its 16-page, 25-millisecond limit and 5-second minimum cooldown. Maintenance responses do not overwrite ordinary adaptive page limits or cooldown state. The native maintenance result must identify maintenance mode and its 128-page chunk bound, report complete status, no checkpoint busy condition, zero remaining free pages and WAL, and coherent checkpoint frame counters. A skipped checkpoint is accepted only when both frame counts are zero. The cycle respects native eligibility, backoff, lease/fence checks, and foreground pressure. Progress is retained by the native phase/cursors and the periodic state. Rollback, stale identity, unknown responses, pressure, a busy checkpoint, or an incomplete reclaim stop the cycle without advancing the success baseline.

The exact `compact_apply` request is stored before dispatch. Pending work first queries `compact_receipt` using that exact request; an applied receipt is incorporated into the saved progress together with clearing the pending request. An unconfirmed acknowledgement can be retried with the same operation ID and unchanged request only while the same owner/fence can still be refreshed, the generation is unchanged, admission remains valid, runtime compatibility is accepted and cancellation has not been requested. A changed generation yields `pending_generation_changed`; a different owner/fence yields `pending_fence_stale`. Neither case discards the request or infers that it did not commit. An unresolved receipt yields `pending_receipt_not_found`. These states preserve the maintenance lease until expiry and require reconciliation evidence before fresh work can proceed.

The reclaim overlap lease uses a 300-second TTL. Native `paraCut` requires at least 120 seconds to remain when its transaction validates the lease, so the extra 180 seconds provide room for latency between lease refresh and transaction validation while staying below the native 900-second maximum.

A saved graph-layout request whose native receipt is not confirmed holds the shared maintenance lease. The tick records `exact_receipt_pending` and returns before the periodic physical-compaction candidate, even when DB + WAL growth has crossed its trigger; the dashboard reports this blocker explicitly. A `not_found` receipt permits recovery only after a refreshed current lease and a fresh status read prove that status still matches the saved pre-dispatch status (or the conservative pre-dispatch phase for a legacy request), the request's original owner differs from the current lease owner, and the current monotonic fence is greater than the request's fence. A persisted transition records the exact old request, `not_found` receipt status, observed native status, verification time, and current owner/fence in a bounded 30-entry `notApplied` history while clearing the pending request; only after that write may the normal path acquire a fresh graph lease and allocate a new request ID. Missing or changed status, an unrefreshable lease, a non-stale owner/fence, or a full history keeps the original request pending and maintenance held. This does not reset native state or bypass the guard.

The periodic candidate establishes its initial growth reference from its first valid comparable sample. In the admitted physical path this is a fresh StateModule `physical` sample with coverage `physical_sqlite_db_wal_v1`; it does not replace `diagnostics.lastComplete` or update `lastSuccessfulCompactionAt`. Subsequent growth maintenance is due at an additional 1,000,000,000 decimal bytes over that reference; the separate maintenance review retains its 24-hour free-page reason. A candidate's terminal compaction receipt does not by itself advance this reference or require manual promotion evidence. Automatic baseline advancement requires exact terminal collection evidence with rows, vectors and GC complete and no retained inline copy, accepted completed layout state, complete native reclaim evidence, and a newer physical sample from the same StateModule action and coverage with the existing category version. That sample is captured before saving the new baseline; it records the current database and WAL sizes, including intervening writes, and does not estimate shrink from batch counters. Physical stats expose no database identity token: same-engine comparability relies on the runtime keeping this action on its configured StateModule endpoint and path, an installation invariant that the sample itself cannot verify. A skipped checkpoint is valid only for a zero-frame response, and the native reclaim result must show no remaining free pages or WAL. Zero pages or bytes reclaimed can still be a successful full cycle; partial reclaim, foreground pressure, cancellation, unknown outcomes, checkpoint contention, or incomparable samples cannot advance it.

Saved periodic growth references are normalized and retained when valid; incomparable samples do not replace them. During the automatic cycle the established baseline changes only after the full completion gate succeeds. Native status still records each applied operation as it happens, and reclaim metrics may record physical bytes returned independently; neither is a substitute for the cycle baseline. Manual incremental migration and ordinary reclaim do not advance this baseline.
