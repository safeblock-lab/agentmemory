# Local reranking

## Qwen3 production provider

Set `RERANK_PROVIDER=qwen` to use the accepted multilingual `Qwen3-Reranker-0.6B` Q8_0 GGUF (639,153,184 bytes). The compatibility default remains `minilm`. Qwen uses the normal candidate reranking path, after indexed retrieval and audience filtering; it never reads the complete graph. Inference is local and incurs no remote embedding/reranking API calls.

Provision `<asset-root>/qwen3-reranker-0.6b-q8_0.gguf` and `<asset-root>/cpu/`. The public CPU runtime ZIP contains the pinned Windows x64 llama.cpp b11371 DLLs and their notices in a `cpu/` folder. CUDA is optional: acquire the two compatible CUDA 12.4 archives from the official URLs and verify the exact hashes in [the GPU acquisition manifest](qwen-gpu-upstream-assets.json), then place their DLLs together in `<asset-root>/cuda/`. AgentMemory's public release does not redistribute CUDA DLLs. NVIDIA's CUDA 12.4 EULA applies to those upstream files; review its distribution terms, including sections 1.1.2, 1.2.2, 2.2 and 2.6. The linked agreement does not state a separate click-through requirement.

Set `AGENTMEMORY_QWEN_ASSET_ROOT` to this same absolute root; the default is `~/.agentmemory/reranker/qwen`. The model is a separate Apache-2.0 asset described in the [model notice](qwen-model-notice.md). Set `AGENTMEMORY_QWEN_PYTHON` to an installed 64-bit Python executable if `python` is unavailable. AgentMemory does not bundle Python. The package ships `dist/qwen-reranker.py`; `AGENTMEMORY_QWEN_SCRIPT` overrides its location for managed deployments. Neither startup nor inference downloads assets or changes global runtime installations.

The scorer verifies the GGUF SHA256 `22c9979ce4fbcdc5acdc310c6641c32797eff1aa980b8f7a2db8a8ea23429a48` and pinned native ABI. Release provisioning must separately verify the runtime archive/file pins. The official instruction/chat prefix and final suffix are tokenized without an added BOS; `yes` token 9693 and `no` token 2152 produce `sigmoid(logit_yes - logit_no)`. This probability becomes `combinedScore`, with stable ties and all result metadata preserved. Retrieved documents are untrusted scoring text, never executed as commands.

`AGENTMEMORY_QWEN_DEVICE=auto` (default) attempts GPU first. It requires at least 2 GiB free GPU memory, warms the entire fixed 4,096-token context, and verifies 29/29 layers plus model, KV and compute buffers on CUDA. Missing/incompatible CUDA or startup allocation failure closes that child before starting CPU. `AGENTMEMORY_QWEN_DEVICE=cpu` skips GPU. Integrity, tokenization, scoring-control, protocol and inference failures propagate; they never silently substitute MiniLM or original scores.

Qwen accepts at most 256 query characters and 8,192 document characters, including the title and narrative separator, and at most 4,096 prompt tokens. Oversized inputs are rejected without truncation. One process handles serialized batches of up to 50 candidates, with eight queued batches, a 60-second queue deadline, a 120-second cold-start deadline and a 55-second inference deadline. Cancellation removes queued work or closes the active scorer. IPC uses bounded JSON lines over owned child pipes, with no network listener. Shutdown closes stdin, allows two seconds for cleanup, then terminates only the owned child and waits up to three seconds for exit. A timeout, cancellation or protocol failure closes the scorer and propagates that request's error. The next request evicts the closed runtime after confirmed cleanup and creates one fresh scorer; the failed request is never automatically retried. Explicit runtime cleanup also preserves loading and cleanup failures.

The previously measured Spanish quality result was 17/18 on a 54-example internal calibration set and was explicitly accepted for release. No independent human review was run; this small set does not establish equivalent relevance across languages or broad answer quality. The integration controls establish scorer parity and device behavior, not a new held-out quality evaluation or a guarantee of sub-minute latency for every corpus/candidate size. Cold preparation, CPU fallback latency and full engine memory remain distinct from warm GPU candidate scoring.

On the validated RTX 3060 Ti host, the production GPU control reproduced the evaluation probabilities exactly (0.9908624286 and 0.0002835427), with 3.47 seconds cold startup, 21 milliseconds for two warm pairs and a sampled joint Node/scorer RSS of 1.04 GiB. CPU uses the native runtime's capability-scored backend selection; the universal x64 backend exceeded the startup deadline, while compatible automatic selection completed the same full-context startup in 51.23 seconds and two warm pairs in 1.59 seconds at 1.19 GiB sampled joint RSS. CPU probabilities differed slightly (0.990734 and 0.0002028) while retaining both correct control classifications. Both owned processes were confirmed gone after cleanup. These are two-pair controls, not 50-candidate latency guarantees.

The optional local reranker scores bounded search candidates with `Xenova/ms-marco-MiniLM-L-6-v2`, using CPU ONNX q8 inference. It does not load the graph or retrieve candidates itself. Indexed retrieval must supply the candidate set first.

## Model and scoring

`AutoTokenizer` receives the query and document separately through `text_pair`; each combined pair is truncated to at most 512 tokens, including special tokens. Query preprocessing is bounded to 256 characters and document preprocessing to 8,192 characters. The model's single raw relevance logit becomes `combinedScore`; it is not a probability or calibrated against hybrid scores. Ties retain candidate order. Successful calls return the first `topK` candidates reranked, capped at 50, preserving the existing public signature and result fields.

One shared tokenizer/model instance serves the process. Whole batches run serially, with at most eight waiting batches. ONNX intra-operation and inter-operation thread counts are both one. Empty/single results, empty queries and invalid limits bypass inference. An overloaded queue returns its input unchanged. A missing model, invalid logit or failed pair returns the entire original batch, avoiding mixed score scales. `isRerankerAvailable()` is true after model loading; sanitized warnings identify loading/inference fallback without logging queries.

## Offline assets

Inference uses `local_files_only: true`. Model files must already exist under `<working-directory>/.cache/agentmemory/reranker/Xenova/ms-marco-MiniLM-L-6-v2/`, using the installed Transformers.js cache layout. This includes tokenizer/config assets and `onnx/model_quantized.onnx`. Source implementation and tests never download these files. Provisioning is a separate deployment step: a controlled download using Transformers.js `from_pretrained` with the same explicit `cache_dir` can populate this directory, followed by process startup. Missing assets remain unavailable for that process lifetime, avoiding repeated failed loads. No global cache is required.

## Limits and verification

The installed Transformers.js API declares `text_pair`, `max_length`, `local_files_only` and ONNX `session_options` in its tokenizer and model options. Offline behavior tests exercise paired inputs, meaningful negative/positive raw logits, stable ties, batch fallback, malformed outputs, concurrency and bounded work.

MS MARCO MiniLM is oriented to English passage relevance. These tests establish the scoring contract; they do not establish equivalent Spanish/code relevance, measured RAM, latency below one minute or scalability to a 10 GB corpus. Candidate recall, ranking quality, actual model availability and combined engine/Node memory must be measured separately. Initial preparation and cold model loading are distinct from warm search latency.
